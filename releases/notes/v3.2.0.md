# Velaris v3.2.0 — The Split, The Boundary, and The Way Back

**Status:** PREPARED 2026-11-08 — final content; the release date is set when it is cut.
**Type:** Minor release — **contains security fixes**
**Upgrade from:** v3.1.2
**Migrations:** 218–231, all additive (no table or column dropped or renamed)

v3.2.0 is the November release. It does three things. It moves four parts of
the platform into services of their own (**the split**). It closes the tenant
boundary wherever one tenant could reach another or the operator's platform
(**the boundary**). And it gives every install backup, restore and recovery it
can prove (**the way back**). Around those: a redesigned Form Builder, connectors
that name their operations, a read-only database query connector, and an update
path rehearsed unattended on PostgreSQL, MySQL and MariaDB.

**Nothing is removed or renamed** — no route, setting, column or script flag.
What changes on upgrade is *who may do what*; the list is in
[What changes for an existing install](#what-changes-for-an-existing-install).

## What changed

### The split — services of their own

- **user-service** (`:8206`) — sign-in and identity: login, MFA, SSO, SAML,
  SCIM, the user directory.
- **portal-service** (`:8205`) — the customer portal, customer accounts and
  portal administration.
- **commerce-service** (`:8207`) — checkout, payments, storefront, marketplace
  and the model market. It calls case-service's `/internal/v1/*` with a new
  internal service secret, which the update generates
  (`VELARIS_INTERNAL_SERVICE_SECRET`); the gateway never forwards `/internal`.
- **worker-service** (`:8208`, health only) — the background jobs, with job
  leases so two processes never run the same job twice.

They join analytics (`:8202`), HxGraph (`:8203`) and HxMigrate (`:8204`). Every
client URL is unchanged: the gateway on `:8200` is still the only door, and each
service listens on loopback only. `VELARIS_WORKERS_<SERVICE>` runs a service as
several processes (it needs the shared cache on).

### Infrastructure

- **PgBouncer connection pooler** (`velaris-pooler`, transaction mode) for a new
  install with the bundled database. An existing install keeps its direct
  connection until its operator turns the pooler on.
- **Valkey as a shared cache** across processes and services.
- **Apache Kafka replaces Redpanda** for the optional event bus. Redpanda v26.2
  would not start without a paid licence. The broker now needs SASL
  (`VELARIS_CASE_EVENT_BUS_USERNAME` / `_PASSWORD`) and starts only when the
  event bus is on — off by default, so most installs run no broker. The update
  removes a leftover Redpanda container and image; its `events-data` volume is
  left for you.
- **OpenBao on raft storage.** OpenBao 2.7 removed the file backend. The update
  copies the encrypted data once, with the same unseal keys
  (`scripts/openbao-storage-migrate.sh`), and keeps the old `openbao-data` volume,
  unmounted, as the way back.
- **Images pinned to exact versions**, checked each release
  (`scripts/check-image-versions.sh`).

### The way back — backup, restore and recovery

- `backup-velaris.sh` takes **one encrypted set** (database, documents, secrets,
  configuration) and records it in the HxDR posture. Every install gets its own
  age key pair; the update generates one where none exists
  (`VELARIS_BACKUP_AGE_RECIPIENT`). The private key is written only to
  `velaris-install-report.md` (mode 0600, never shipped). **Keep it somewhere
  else as well** — without it a backup cannot be restored.
- `restore-velaris.sh <set> --key <file>` restores an install and then proves it.
- A **warm standby** (sync, read-only serving and a tunnel, as systemd units),
  with its status reported.

### Form Builder, redesigned

Sections, conditions, versions and drafts (migrations 226, 227), connector
lookups, translations and field-level security. A form and everything stored
through it is checked against the form: a submission stores only the form's own
keys; hidden fields never reach a portal browser; a designer's regular
expression that can backtrack catastrophically is never run; a malformed form
definition cannot crash a submit.

### Connectors

- **Named operations.** A connector lists its operations (`{key, label, method,
  path}`) and a saved form field or step chooses one. The path is always the
  saved one, never the caller's.
- **Database query connector** (`sql_query`). Saved, read-only SELECTs on your
  own PostgreSQL, MySQL or MariaDB database. No SQL is taken at run time: a form
  names a saved query, and its inputs fill bind parameters only. Each query runs
  in a read-only transaction with a time limit (≤ 30 s) and a row cap (≤ 1000);
  a value over 16 KB arrives as NULL, and a result stops at 200 KB. `aiomysql` is
  now a core dependency, so any install can reach a MySQL database.
- **A large response is readable.** A response over the overflow threshold is
  stored and the call records a `ref_url`. That URL had no route; it is now
  `GET /api/v1/hxbridge/overflow/{call_id}` (connector read permission, own
  tenant only).
- A dead-letter retry runs the same operation it failed on.

### Updates and rollback

Found by rehearsing an unattended update of a clean 3.1.2 install, on all three
databases:

- **MySQL and MariaDB installs can now be updated** — backup, migrations and the
  release manifest run against your own database server. **A 3.1.2 MySQL/MariaDB
  install runs 3.1.2's updater, which still refuses: run this release's
  `update-velaris.sh` by hand once.**
- A rollback no longer leaves sign-in broken; the health check tries a request
  in each part of the API, not just `/health`.
- An update from your own update server keeps `velaris.yaml`'s source, server,
  channel, schedule and database settings.
- A tarball update removes the files the previous release shipped and this one
  does not. Files you added are untouched, and nothing outside the install —
  nor `.env`, keys, certificates, backups or data — is ever removed.
- An update stopped halfway is finished on the next run.
- An update no longer fills in a setting you left empty. Only new settings get
  values.
- `scripts/package-release.sh` builds the tarball an update server serves.

### Operations

- No single empty or mistyped line in `.env` stops a service: the default is used
  and the log names the variable.
- Studio → Status lists every dependency as working, degraded or off, with the
  reason; so does the end of every update.
- `./support-bundle.sh` — a fault report with secrets and personal data removed.
- A default Prometheus alert set; the bundled Prometheus can now reach the
  platform.
- A tenant's administrator sees **their own tenant's** logs, metrics, AI-call
  records and security events (HxLogs, Observability, LLM Ops, Enterprise, the
  audit stream); the operator sees everything.
- Operator documentation: `docs/operator/` and the Operator Guide PDF.

### Security

Every item was reproduced first and has a test.

- **Tenant administration.** A tenant's admin could rewrite the built-in roles
  and system-wide portals, and put another tenant's roles or users in their
  groups; create, change and delete tenants (and raise their own limits); bind
  any account, the operator's included, to an SSO identity they own. All refused.
- **Website demo sign-ups** were made admin of the install's default tenant — the
  operator's. Each sign-up now gets its own demo tenant, expiring after 7 days.
  The website holds a credential that opens the demo routes only
  (`VELARIS_DEMO_PROVISION_SECRET`; empty = sign-ups stay queued).
- **Archived tenants stay closed**: their people are refused on every request,
  their agents and MCP grants stop, and their portal answers 404.
- **Outbound requests.** A tenant's connectors, database sources, mail hosts and
  HxDeploy webhooks reach the internet only, checked when saved and again at
  connect, and connected by the checked address (DNS rebinding). Verified TLS
  checks the certificate against the host name while connecting to the pinned
  address. The operator's own connectors keep their LAN targets.
- **Case work.** Creating a case and completing, claiming, reassigning or deleting
  a step needs an access group (the assignee's, a shared one, or their manager).
  A user id in a request body must be the caller's.
- **Form lookups** run only what a saved form says: its connector, its operation,
  its mapped inputs.
- **Portal customer tokens** were signed with a key that is in the source. They
  now use the install's own key.
- **Platform screens** — the audit chain, audit-stream targets, HxLogs,
  observability metrics, internal status — are the operator's.
- `/metrics` and `/health/deep` are refused to any request that came through a
  tunnel or proxy front.
- Rate limits are per client address and cannot be dodged by a forged header;
  sign-ups have an hourly cap (`REGISTER_GLOBAL_MAX_PER_HOUR`, 60).
- The MySQL/MariaDB password no longer appears on a command line. An empty or
  mistyped `VELARIS_CASE_HXGUARD_CASE_ENFORCEMENT` stays enforced. The Helm chart
  generates its own token secret per install instead of a default from the source.

## What changes for an existing install

Nothing switches itself on, with two recorded exceptions: the update generates
an **internal service secret** and a **backup key pair** where an install has
none. What changes is who may do what:

1. **A user in no access group can no longer create cases or complete work**
   (platform `admin` included; `superadmin` passes) until an administrator
   assigns a group. Run `scripts/grant-access-group.sh` first without `--apply`
   to see who is affected, then with it.
2. **Portal customers are signed out once** and sign in again with an emailed
   code.
3. **A tenant's administrator** loses the operator's tenant-less connectors and
   records and the platform-wide screens (403, 404 or an empty list). The default
   tenant — the operator — is unchanged.
4. **Existing website demo accounts** keep their default-tenant powers until
   `move_demo_accounts.py --apply` runs (registration-service container). They
   are moved and emailed.
5. An old Studio tab left open during the update may get a 403 on a form lookup
   until it is reloaded.

## Upgrade notes

- **From v3.1.2 only.** From an earlier release, update to v3.1.2 first.
- Run `./update-velaris.sh`. It takes a backup first and stops if the backup
  fails, migrates OpenBao to raft once, and applies migrations 218–231.
- **MySQL / MariaDB:** run this release's `update-velaris.sh` by hand once (see
  above).
- **systemd installs:** the update ends with
  `deploy/systemd/refresh-after-update.sh`, which now also installs the units for
  the new services.
- After the update: copy the backup private key out of
  `velaris-install-report.md`, then run steps 1 and 4 above.
- New settings, all unset = the previous behaviour, are listed in the
  documentation (Environment Variables → *Settings Added in v3.2.0*).

## How it was tested — and what was not

- **Upgrade rehearsal (R3):** an unattended update of a clean 3.1.2 install on
  PostgreSQL, MySQL and MariaDB, with rollback. Passed on all three, 2026-11-01.
- **Soak (R6):** on an 8 vCPU / 16 GB box, about 600 active users with
  sub-second pages and no errors.
- **Failure (R6):** under 100 users, case-service, user-service, PostgreSQL,
  Valkey, PgBouncer, the gateway and the whole box were each killed (SIGKILL).
  Each came back alone; every case the platform had confirmed was in the
  database (852 of 852); after the fixes, an outage answers 503, never 500.
- **Security:** each fix was reproduced live first, then proven refused as the
  least-privileged user who should be refused, and allowed for the one who
  should succeed.

**Not proven yet:** a Kubernetes scale-out under load; a sustained flood; a
published sizing table; a Temporal worker stall seen once under soak. A crash of
OpenBao alone comes back sealed until a unit starts (running services are
unaffected). Studio's development proxy answers 500, not 502, while the gateway
is down. These are
the first work of December, ahead of an independent penetration test.
